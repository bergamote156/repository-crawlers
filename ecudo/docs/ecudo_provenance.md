# OAI-PMH Provenance for ECUDO Records

This document describes how to generate OAI-PMH provenance information for
ECUDO records when Onedata acts as an aggregator.

## Background

When Onedata aggregates datasets from external sources (like ECUDO) and exposes
them via OAI-PMH, it should include provenance information to trace the origin
of metadata records. This is required for OpenAIRE compatibility as an aggregator.

**References:**
- [OpenAIRE Guidelines - Compatibility of Aggregators](https://openaire-guidelines-for-literature-repository-managers.readthedocs.io/en/v4.0.0/use_of_oai_pmh.html#compatibility-of-aggregators)
- [OAI-PMH Provenance Guidelines](https://www.openarchives.org/OAI/2.0/guidelines-provenance.htm)

## OAI-PMH Record Structure

A complete OAI-PMH record consists of three parts:

```xml
<record>
  <header>
    <identifier>oai:onedata.org:...</identifier>
    <datestamp>2024-12-10</datestamp>
  </header>
  
  <metadata>
    <!-- OpenAIRE XML generated by openaire.py -->
    <oaire:resource ...>
      ...
    </oaire:resource>
  </metadata>
  
  <about>
    <!-- Provenance information - described in this document -->
    <provenance ...>
      ...
    </provenance>
  </about>
</record>
```

The `openaire.py` module currently generates only the `<metadata>` content.
The `<about><provenance>` section needs to be added when serving records
via OAI-PMH.

## Provenance XML Structure

```xml
<about>
  <provenance xmlns="http://www.openarchives.org/OAI/2.0/provenance"
              xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
              xsi:schemaLocation="http://www.openarchives.org/OAI/2.0/provenance
                                  http://www.openarchives.org/OAI/2.0/provenance.xsd">
    <originDescription harvestDate="2024-12-10T14:30:00Z" altered="true">
      <baseURL>https://odis.ecudo.pl//</baseURL>
      <identifier>urn:SDN:CDI:iopan.pl:uuid:0cd81dda-1260-40b0-b917-1e2419e93d76</identifier>
      <datestamp>2022-10-08</datestamp>
      <metadataNamespace>https://project-open-data.cio.gov/v1.1/schema/catalog.jsonld</metadataNamespace>
    </originDescription>
  </provenance>
</about>
```

## Field Definitions and Mapping

### originDescription Attributes

| Attribute | Description | Value for ECUDO |
|-----------|-------------|-----------------|
| `harvestDate` | UTC datetime when the record was harvested | Generated at harvest time (e.g., `2024-12-10T14:30:00Z`) |
| `altered` | Whether the record was modified before re-dissemination | Always `true` (JSON-LD → OpenAIRE XML transformation) |

### originDescription Elements

| Element | Description | Source | Example |
|---------|-------------|--------|---------|
| `baseURL` | URL of the originating repository | Constant for ECUDO | `https://odis.ecudo.pl/` |
| `identifier` | Original identifier in source repository | `EcudoRecord.identifier` | `urn:SDN:CDI:iopan.pl:uuid:...` |
| `datestamp` | Last modification date in source | `EcudoRecord.modified` | `2022-10-08` |
| `metadataNamespace` | Namespace/schema of original format | Constant for ECUDO | `http://www.w3.org/ns/json-ld#` |

## Important Clarifications

### datestamp vs issued

**`datestamp` is NOT the publication date!**

| Field | Meaning | ECUDO Source |
|-------|---------|--------------|
| `datestamp` | Last modification of the **metadata record** | `modified` field |
| Publication date | When the **resource/dataset** was published | `issued` field |

The OAI-PMH `datestamp` indicates when the metadata was last updated, used for
incremental harvesting. It is distinct from the resource's publication date.

### metadataNamespace for JSON-LD

The OAI-PMH provenance specification assumes XML metadata with XML namespaces.
Since ECUDO provides JSON-LD (not XML), we could use the `@context` URL 
from the JSON-LD record as the logical equivalent of a namespace:

```
https://project-open-data.cio.gov/v1.1/schema/catalog.jsonld
```

but it doesn't work, so we use the constant for ECUDO instead:
```
http://www.w3.org/ns/json-ld#
```

This identifies the schema/vocabulary used in the original metadata format
(Project Open Data / DCAT).

### altered = true

The `altered` attribute must be `true` because:
1. Format changes from JSON-LD to OpenAIRE XML
2. Schema transforms from DCAT to DataCite/OpenAIRE
3. Field mappings are applied (e.g., `publisher.name` → `datacite:creator`)

## Data Availability in EcudoRecord

Most provenance data is already available in `EcudoRecord`:

| Provenance Field | Available in EcudoRecord | Notes |
|------------------|--------------------------|-------|
| `identifier` | ✅ `record.identifier` | Directly available |
| `datestamp` | ✅ `record.modified` | Directly available |
| `metadataNamespace` | ❌ `record._raw["@context"]` | From preserved raw JSON-LD |
| `baseURL` | ❌ | Constant, can be global config |
| `harvestDate` | ❌ | Must be captured at harvest time |
| `altered` | ❌ | Always `true`, no storage needed |

### Implementation Notes

When implementing provenance generation:

1. **Constants** - Define as module-level constants:
   ```python
   ECUDO_BASE_URL = "https://ecudo.pl"
   ECUDO_METADATA_NAMESPACE = "http://www.w3.org/ns/json-ld#"
   ```

2. **Harvest timestamp** - Must be captured when crawling and passed through
   the processing pipeline (not currently stored in `EcudoRecord`).

3. **XML generation** - Can be added as a new function in `openaire.py` or
   a separate module for OAI-PMH record wrapping.

## Provenance Schema

The provenance XML must validate against:
```
http://www.openarchives.org/OAI/2.0/provenance.xsd
```

Key constraints:
- `harvestDate` and `datestamp` must be valid UTC datetime or date
- `baseURL`, `identifier`, and `metadataNamespace` must be valid URIs
- Nested `originDescription` elements are optional (for multi-hop provenance)
